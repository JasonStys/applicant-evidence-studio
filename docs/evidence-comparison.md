# Criterion evidence comparison

Created by Jason Stys. This workflow helps an authorized workspace user review two applicant records against the same professional rubric. It does not select a winner, recommend a hiring outcome or infer protected traits, degrees or employment years.

1. In Review queue, tick **Compare ID** for exactly two records. A third choice is disabled until one is removed. IDs remain selected across queue filters/pages; use **Clear comparison selection** to start over. Display names are not added to the comparison.
2. Choose the intended job rubric and click **Capture selected evidence**. Both records require recorded processing authorization. A missing/deleted record or changed rubric fails visibly and can be retried after refreshing the selection. The capture is read-only: it does not revise records, ranks, review states, consents or the encrypted workspace.
3. Review each criterion's common target, weight and required flag. Cells show reviewed target attainment, the strongest contributing evidence ID/strength/kind/summary, source ID/label, locator and warnings. Alternative reviewed claims and excluded unreviewed claims are counted without multiplying coverage. Missing reviewed support is **unknown ability**, not proof of inability. Original source bodies remain in the existing record review; **Open original record ID** opens that authorized workflow.
4. Review flags and clarification prompts. Incomplete rubric evidence can prompt an authorized source or accessible work sample. An explicitly unclear education outcome or missing transfer destination prompts factual clarification; no degree, failure or paid work duration is invented. Education and employment-month totals do not enter criterion scoring.
5. Optionally type human observations (maximum2000 characters) and download the private comparison JSON. Observations are transient until exported and never alter scores. The exact captured report includes record revisions, full record SHA-256 fingerprints, rubric fingerprint and capture timestamp. There is no fresh API read on download. Fingerprints identify snapshots, including omitted private fields; they are not ranking inputs, anonymization, signatures or proof that claims are true.

Changing selection/rubric, running a record mutation, opening an original record, locking or leaving the comparison invalidates its displayed capture and observations. The original-record buttons explicitly advise downloading first to preserve observations. Pending old results cannot replace the new context. A report already downloaded is a historical snapshot; it cannot be revoked or updated automatically.

## Privacy and access

Private-account owners operate entirely within their unlocked browser: the existing ciphertext account service gains **no plaintext comparison endpoint**. A single cloned workspace provides the two records and rubric; comparison/export sends no API or encrypted-save request. Lock/unmount clears the UI and invalidates pending work. Existing independent-user authorization, crypto and conflict gates remain enabled. There are no new user roles, sharing links, people searches or external AI calls.

Legacy trusted developer mode uses authenticated `GET /api/comparison?job_id=...&left=...&right=...`. A single parameter-bound SQLite read transaction captures one rubric and exactly two record bodies/revisions. Missing authorization401, untrusted Host/Origin403, missing records/rubric404, duplicate IDs or unconfirmed processing authorization422. Host security headers/no-store behavior remain. This mode already stores plaintext locally; it does not gain the private-account host-encryption guarantee.

The explicit JSON export is **unencrypted private information**. It omits display names, source bodies, personal notes, job description and employment-month totals, but user-written evidence summaries/source labels/observations may still contain personal information. Keep downloads private; this feature does not claim anonymization, bias freedom, compliance, production hiring readiness or statistical prediction. People must review original applications and make their own decisions.

## Implementation and validation

`web/comparison.ts` validates/clones a bounded two-record capture, reuses the existing deterministic assessment/fingerprint logic and constructs only the documented report fields. `web/EvidenceComparison.tsx` handles explicit capture, stale-context guards, responsive keyboard-scrollable matrix, original-record navigation and exact JSON export. `App.tsx` manages the two-ID queue selection. `Store.comparison_capture` and the legacy API provide atomic authenticated input; `privateAPI` performs its counterpart locally from one clone. No new scoring formula or automatic decision rule is introduced.

`npm run test:comparison` compiles the actual domain with Vite and runs independent Node examples:3:1 weights,2/3 practice,1/4 declaration, Python-compatible81.25→81.2 rounding, duplicate/unreviewed exclusions, non-scoring identity/chronology changes, explicit unknowns, immutable capture, authorization/schema errors and private-field omission. `tests/test_comparison.py` checks API boundaries/no writes and a real concurrent SQLite writer. Existing full legacy/private browser matrices also exercise actual comparison/citations/downloads, Python reference assessment parity, no plaintext network/save, stale delayed responses, lock, mobile scrolling and Axe.
